# System audit, October 2, 2026

Scope: NOHM server on current `main` (`the-nohm-application-1.1` @ `12d7cf6`, after the lead's fourteen security commits), the website's `web-booking` branch (`/book`, `/join`, `/join/renter`), and the two unmerged server branches. Method: three independent reviewers (server security, website-to-server contract, cold code review of the website), every finding re-read in the code by me before it went in here. Nothing below is a "possible issue"; each is a line of code and how it fails, or a thing checked and found fine.

## The one serious server finding

**HIGH: the arrival PIN is handed to the contractor by the mutation endpoints.** Confirmed in the code.

The PIN is the anti-fraud gate: `submitDiagnosis` refuses until `verifiedAt` is set (`backend/src/modules/jobs/job-diagnosis.service.ts:272`), and estimate → hold → capture hang off it. The read paths scrub it (`job-queries.service.ts:210, 279`; `now-queries.service.ts:172, 200, 290, 435`). The write paths don't:

- `PATCH /jobs/:id/status` with `EN_ROUTE` (contractor): `job-progress.service.ts:239-248` mints `arrivalPin`, `:482-485` returns `prisma.job.findUnique({ include: JOB_INCLUDE })`, the whole row, PIN included. The controller returns it as-is (`jobs.controller.ts:509`).
- `POST /jobs/:id/arrive` (`job-check-in.service.ts:342-345`) returns the full row.
- NOW: `POST /now/jobs/:id/en-route` and `/arrived` (`now-visit.service.ts:356-390, 526-635`) return the row from `moveAsSeen`, which mints the PIN.

The app already parses the field (`app/lib/models/job.dart:105`). A pro taps "On my way", reads `arrivalPin` from the JSON, posts it to `/jobs/:id/verify-arrival`, gets `verifiedAt`, and can diagnose, estimate and be paid without being at the door.

**Fix:** every contractor-facing return goes through the existing scrubbers (`{ ...job, arrivalPin: null }` / `_hydratedForContractor`); add a spec asserting the four responses carry `arrivalPin === null`. One file each, no schema change.

## Server: Medium and Low

- **M1. Admin password sign-in has no second factor** (`auth-admin-login.service.ts:35-96`). A phished admin password is full control (refunds, holds, restrictions). Fix: passkey or texted code after the password for `role === ADMIN`, or passkey-only for admins by default.
- **M2. Refresh rotation without reuse detection** (`auth-session.service.ts:33-90`). A stolen refresh token used before the real device refreshes wins a fresh pair; the victim's next refresh 401s and nothing is revoked or logged. Fix: keep the previous hash on the session; a superseded token presented → deactivate the session, log it.
- **L1. `@Body('x')` primitives bypass the ValidationPipe**: `jobs.controller.ts:310, 325, 433, 495, 592`; `hin-vault.controller.ts:77-78`; `chat.controller.ts:111`; `notifications.controller.ts:81`; `maintenance.controller.ts:118`; `tenants.controller.ts:58`. Each traced: no bypass, but bad input becomes a 500. One small DTO each.
- **L2. `capturePayment` has no AUTHORIZED→CAPTURING claim** (`stripe-job-payments.service.ts:411-430`). Two callers both hit Stripe; Stripe refuses the second (no double charge) but the loser trips the unique event key after success. Today guarded upstream by `confirmCompletion`'s claim. Fix: `updateMany` claim first.
- **L3. Google Maps keys in the mobile app** (`AndroidManifest.xml:109`, `AppDelegate.swift:14`, Firebase plists). They ship in the binary anyway; confirm the key is restricted to the package/bundle in Google Cloud. No `sk_live`, AWS, Twilio, private keys or `.env` files anywhere.
- **L4. `POST /predict/brain/feedback`** binds the home but not the finding (`predict.controller.ts:168-172`). Already in `docs/SECURITY.md` "still open".
- **L5. `/auth/check-exists`** is a throttled account-enumeration oracle. Acceptable for a phone-first product.
- **L6. `docs/SECURITY.md` "still open" is stale** (good news: sign-in codes are HMAC digests; Certn webhooks refused in prod without a secret). Update it.
- **L7. `POST /auth/logout` ends every session**, not the device's (`auth.controller.ts:325-331`). Signing out on nohm.app signs the phone out too. Pass `user.sessionId`.

## Server: checked and fine

Every `:id` route traced to an ownership check (jobs, properties, home members, HIN vault, appliances, invoices, NOW, rentals, maintenance, emergencies, tenant invites, contractor invites, disputes, no-show, weather, device monitor, predict, AI conversations, notifications, Three Quotes, chat). Stripe webhooks verified on raw body and idempotent; holds are manual-capture with server amounts, `shownFeeCents` only compared; transfer destinations are the job's own contractor / the lease's own landlord; credits can't go negative or double-apply; Three Quotes deposit math is BigInt half-up. OTP: NANP only, budgets, cooldown, HMAC at rest, atomic attempts, single-use, constant-time compare. Google/Apple tokens checked for audience and issuer. Production refuses to boot without two distinct ≥32-char JWT secrets, a non-local `CORS_ORIGIN`, Stripe and S3 vars. All job status writes go through `JobStatusWriter`; races claimed with guarded `updateMany`. `JOB_INCLUDE` gives the pro no homeowner phone; the homeowner never sees license or insurance numbers; no HIN or PIN in push/SMS bodies; no `passwordHash` in any admin response; request logger redacts auth, password, pin, otp, token, phone, email. Uploads use random keys, MIME allowlists, `..` rejected. Raw SQL parameterised or whitelisted. Admin panel: tokens in `sessionStorage`, all authorization server-side.

## The website against current main

All 50 endpoints the site calls exist on `main` with the exact method, path, auth and role the site assumes. Every body matches its DTO field for field (nothing extra for `forbidNonWhitelisted`, nothing required missing). No captcha, no app-version gate, no rule against `deviceType: 'web'`. The polls (Stripe status 5 s, NOW 15 s, offers 2 s×10) sit well under the 100/min per-user limit.

Mismatches found and **fixed in `221b722`**:
- Trusted devices never worked from the web: `verify-device-otp` returns a `deviceSecret` the site dropped, and `email-password` never sent it back. Now kept and sent.
- `PRO_UNAVAILABLE` / `PRO_JUST_BOOKED` don't exist on the server; a NOW dispatch that loses the race is a plain 409. Now routed to "pick again" with the live list refreshed.
- A 409 on `POST /jobs` retried forever. Now once, then the key is retired and the person is told.
- `dash.profile.attestedName` isn't on the dashboard; the agreement screen now shows the signed date.

Owner setting to know: the site's `googleClientId` must equal the server's `GOOGLE_CLIENT_ID` (the server verifies audience against that one value; `webClientId` in config is never read).
